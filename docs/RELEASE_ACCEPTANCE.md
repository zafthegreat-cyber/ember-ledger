## Scope and status rules

The finish line is a usable, recoverable, authorized app with the existing Collect, Find, Sell, Bot and Business structure preserved. Existing manual and local capabilities remain useful while connected capabilities are completed. A planned integration must not become a live capability merely because its screen, adapter or schema exists.

The user's latest instruction authorizes continued implementation. Earlier “report, then stop” recommendations are no longer the local implementation plan. Separate approval is still required for commit, push, merge or deployment. Owner-data migration, destructive recovery, provider connection and other external actions require their concrete operational prerequisites; this inventory neither activates nor authorizes them. Existing retailer, remote-execution, Import Review and human-confirmation safeguards remain requirements.

| Status | Meaning |
|---|---|
| `verified` | The bounded capability has source and recorded test or inspection evidence in the stated environment. Local or synthetic verification is not live-provider or production proof. |
| `implemented-unverified` | Relevant implementation exists, but required database, hosted, device or end-to-end evidence is missing. |
| `missing` | The acceptance behavior is absent or incomplete. The evidence column identifies any reusable foundation rather than treating the whole area as unbuilt. |
| `external-blocked` | The next acceptance step needs access, authorization, credentials, provider terms, physical hardware or a release decision outside local code. Local preparation can continue. |

There is no measured overall percentage. Test counts are evidence for their specific scenarios, not percentages of the product. “Complete” requires every included release requirement to be verified at its stated target environment. Optional roadmap scope must be explicitly included or deferred; deferred functionality must remain honestly unavailable.
