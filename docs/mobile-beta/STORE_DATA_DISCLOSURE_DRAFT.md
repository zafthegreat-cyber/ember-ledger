# Code 3 TCG — store data disclosure draft

Prepared October 18, 2026 for owner review. Publisher: **Anchor & Wing LLC DBA Code 3 TCG**. Privacy contact: **support@code3tcg.com**. Package: `app.code3tcg.mobile`.

This is a source-based worksheet for Apple App Privacy and Google Play Data Safety, not a submitted form or a legal compliance determination. It describes the current native candidate and its connected web services, including optional owner/business features. Production privacy changes, physical-device checks, and the decisions below remain open. Do not answer “no data collected.”

## How to use this draft

Apple distinguishes retained off-device data from processing only for the immediate request, and asks about linkage, purposes, and tracking. Optional features are not automatically exempt. Account-linked records below should normally be marked **linked to the user**; hashing a mailbox reference does not make it anonymous. [Apple App Privacy guidance](https://developer.apple.com/app-store/app-privacy-details/).

Google includes off-device ephemeral processing in the form, with a separate ephemeral designation. Some provider processing and intentional user sharing can qualify for sharing exceptions; confirm the conditions for each flow. The form applies to closed/open testing; internal-only testing is currently exempt. [Google Data Safety guidance](https://support.google.com/googleplay/android-developer/answer/10787469).

The category mappings below are draft answers based on app behavior. “Optional” means the feature or input is optional, not that disclosure can be omitted. Confirm the actual required/optional answer across every enabled account tier and region before submission. Account data is required for the signed-in service; the limited preview must not be treated as proof that every feature works without an account.

## Precise location and public listing separation

In [App.jsx](../../src/App.jsx), `enableLocationTracking` around lines **15404–15419** calls `getCurrentPosition` and saves coordinates using `toFixed(4)` to `locationSettings.manualLocation`. [Hosted supplement](../../src/features/persistence/hostedAppSupplement.js) includes `locationSettings`; [backup sources](../../src/features/backup/backupSourceRegistry.js) and [cloud capture](../../src/features/persistence/cloudWorkspaceSources.js) include the corresponding saved source. The current code therefore supports retained, account-linked precise location.

The initial review found that `listingFromSource` copied this private setting into a new listing's `locationCity`. The local fix now starts that public field empty for every source (manual, inventory, collection and catalog). The existing field is labeled **Public city** with visible guidance to choose the city for the listing and keep home addresses/exact locations private. Users must enter their public choice themselves; saved listings and existing drafts retain their previously chosen city when reopened or edited. No stored location or listing was rewritten. [Marketplace location regressions](../../scripts/test-marketplace-location-privacy.mjs) pass 18 synthetic scenarios using private GPS, home-address and home-city fixtures across new and existing listings.

Both-phone verification of the final field and permissions remains required. This fix does not change precise-location cloud saving, erase older listing values, prevent users typing private details themselves, or make disabling location permission erase a previously saved value.

## Recipients, sharing and tracking decisions

- **Supabase / Vercel:** account, storage, database and hosting/API providers. Treat relevant information as collected; confirm processor terms before applying Google's service-provider sharing exception.
- **Other users / workspace members / administrators:** public contributions, explicitly shared workspace records, moderation and support have distinct visibility. Verify their previews and permissions. Do not claim all saved content is private.
- **External content / integrations:** OpenStreetMap tiles, catalog/image hosts, retailer links and optional eBay/provider tools can receive network metadata or the requested search/area. Review the actual release configuration and each recipient's independent use; do not assume every external recipient qualifies as a processor. Native export/share deliberately hands selected files to an app chosen by the user. [Map component](../../src/components/ScoutTileMap.jsx), [eBay client](../../src/features/flipScout/ebayClient.js), [native file sharing](../../src/native/nativeFiles.js).
- **Advertising/tracking:** no advertising SDK or advertising-ID access was found in the reviewed source/dependency search. The [iOS manifest](../../ios/App/App/PrivacyInfo.xcprivacy) currently says `NSPrivacyTracking=false`. Those facts support further review, not a blanket verified “no tracking” assertion. The owner must confirm no advertising, cross-company profiling, data-broker transfer or independently tracking embedded service is enabled. Do not invent marketing uses from locally generated marketing-copy helpers.

## Retention, security and deletion answers

Use the [public policy source](../../src/config/privacyPolicy.js), [receipt/backup audit](./RECEIPT_PRIVACY_AUDIT_2026-10-18.md) and [Vercel audit](./VERCEL_RETENTION_AUDIT_2026-10-18.md) together:

- Supabase Pro and daily physical database backups were verified. Its documented backup/log access window is seven days; PITR is not enabled. Database backups contain file metadata, not uploaded-file bytes.
- Vercel is on Hobby with documented one-hour runtime-log availability. Build logs are separate and retained indefinitely per deployment. Neither provider has a configured log drain in the inspected settings.
- These are availability/configuration facts, **not permanent-erasure deadlines**. Provider-internal security/support records, effective purge schedules, independent operator copies and support-mailbox retention still need a documented owner/provider decision.
- Native API destinations require HTTPS, Android disallows cleartext traffic, and the mailbox adapter requires verified TLS. Verify all enabled remote content and integrations before marking the entire app's transit-encryption answer complete. Do not describe cloud storage as end-to-end encrypted: the service can read the records it processes.
- Isolated hosted deletion acceptance passed **67 checks** against real Supabase Auth, PostgREST and Storage using disposable accounts and the actual Express routes. It covered private-file isolation, failure/retry, session revocation, hard deletion and another account's data preservation. The temporary branch and both restricted local test-key files were removed; cleanup was verified. Production/shared-price writes were zero. [Hosted acceptance and cleanup report](./HOSTED_DELETION_ACCEPTANCE_2026-10-18.md).
- Production enablement, the production HTTPS/CORS endpoint, deployed deletion UI and physical-phone flows remain unverified. Use the staged [deletion rollout](./ACCOUNT_DELETION_ROLLOUT.md); the loopback-HTTP staging harness is not a production or phone pass. Downloads, copies on other devices and records held by others are not remotely erased. Shared ownership can require transfer before account deletion.

## Owner acceptance before entering final store answers

1. Decide the actual target age groups and whether children directly use the app, versus adults managing family requests. Review the child-data flow and store audience requirements; do not select a Kids/Families designation simply because the brand is family-friendly. [Google Families policy](https://support.google.com/googleplay/android-developer/answer/9893335), [Apple review guidelines](https://developer.apple.com/app-store/review/guidelines/#privacy).
2. Confirm the enabled release features, providers, support-mailbox handling, marketing/tracking practices, and required versus optional fields. Reconcile these answers with the iOS privacy manifest and dependency manifests.
3. Verify the new public-city field and both physical-device permission/data-transfer flows. Keep the precise-location disclosure: the listing fix does not remove saved GPS from cloud scope. The Android manifest requests camera, coarse and fine location; iOS usage strings cover camera, photo library and location. Permissions alone do not establish what is transmitted. [Android manifest](../../android/app/src/main/AndroidManifest.xml), [iOS Info.plist](../../ios/App/App/Info.plist).
4. Finish the production receipt privacy rollout: the audited `receipts` bucket remains public. Private-bucket owner/anonymous/other-account behavior passed on the isolated branch; production still needs the authenticated resolver deployed before changing privacy, preservation of the existing object/path/bytes, and live access checks. [Compatibility plan](./RECEIPT_PRIVACY_COMPATIBILITY.md).
5. Use the completed hosted deletion/retry evidence to proceed with the reviewed production rollout. Verify production HTTPS/CORS, deployed UI and both physical-phone flows after enablement. Intended links: [Privacy](https://code3tcg.app/privacy), [Support](https://code3tcg.app/support), [Delete account](https://code3tcg.app/delete-account). Their presence in source is not proof the current production release serves them.
6. Resolve remaining provider/operational retention questions and approve the final store checkboxes. This review did not submit either form or grant an independent-security/Families compliance badge. Track completion in [readiness](./READINESS.md).
