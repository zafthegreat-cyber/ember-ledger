### Transfer implementation and verification

Settings now offers **Move to a new device**. Its account-linked transfer file combines the existing verified device backup with an optional fresh cloud backup and supported cloud attachment bytes. Comparison checks record identifiers and content, not counts alone, plus cloud file paths, sizes and SHA-256. Equal counts with replaced IDs or altered attachments fail comparison. Original storage, source cloud records, and sync baselines are not written by preparation or comparison.

The same file opens the existing recovery screen with separate device and cloud previews. Device recovery adds missing records while retaining current versions and settings; cloud recovery retains existing records and refuses to replace different file bytes. Both continue through existing account verification. Unclaimed/other-account drafts, pending recovery, account switches, source edits during export, damaged packages and unavailable cloud reads fail closed. Device-only offline mode states its coverage limits. Unsaved session drafts and non-embedded local file references remain visible limitations; keep the original app until those are checked.

Validation on synthetic data: 15 transfer scenarios; 23 existing workspace recovery checks; 20 cloud-sync checks; 15 cloud-backup checks; existing backup verification (22 sections, 34 records). Chromium verified actual file export, file comparison, device/cloud recovery previews, password gates, zero comparison writes, keyboard focus, 44px controls and no horizontal overflow at 320, 390 and 1440 pixels in both themes. A second six-case run mounted the actual CloudSyncPanel with app styles and Settings wrappers: text contrast passed at 4.5:1 or better, and 390-pixel light/dark screenshots were visually inspected. Screenshots/results: `artifacts/qa/mobile-beta/device-transfer/`. These are browser tests, not physical Android/iPhone verification. No production records or existing account data were imported, modified or deleted.

Apple requires in-app initiation of account deletion and removal of associated data unless retention is legally required. Ordinary apps should not require a support call or email to complete a standard deletion. Google's account-deletion requirements include an in-app path and a functional, readily discoverable outside-app resource that can be used without reinstalling. The implemented route must therefore be published and the hosted service verified before submission; a saved request or support-only path is not sufficient evidence of working fulfillment. [Apple account deletion](https://developer.apple.com/help/app-review/guideline-reference/5-1-1-account-deletion), [Google account deletion](https://support.google.com/googleplay/android-developer/answer/13327111?hl=en).
